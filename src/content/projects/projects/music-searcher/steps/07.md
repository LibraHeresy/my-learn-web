## 技能清单：这个项目帮你练熟了哪些技术

### 硬技能（具体的代码能力）

| 技能 | 在项目中的具体应用 | 熟练掌握的标志 |
|------|-------------------|---------------|
| **fetch API** | 发送 HTTP GET 请求到 iTunes API，获取 JSON 数据 | 你能不查文档写出 `await fetch(url)` + `await response.json()` 的完整流程 |
| **async/await** | 用同步写法处理异步逻辑，整个 `doSearch` 函数都是 async 函数 | 你能解释 `await` 后面的代码什么时候执行，以及为什么要在 async 函数里用 |
| **try/catch 错误处理** | 捕获网络错误、HTTP 非 200 错误，并展示友好提示 | 你能区分"意料之中的错误（网络断）"和"意料之外的错误（代码 bug）"，并分别处理 |
| **防抖（debounce）** | 用防抖控制搜索请求频率，避免每次按键都发请求 | 你能在不查资料的情况下写出防抖函数，并解释 `clearTimeout` + `setTimeout` 的配合逻辑 |
| **URL 编码** | `encodeURIComponent()` 处理中文搜索关键词 | 你知道为什么 URL 中不能直接放中文，以及编码后是什么样子 |
| **JSON 数据解析** | `response.json()` 把 API 返回的 JSON 文本转为 JS 对象 | 你能看着 API 返回的原始 JSON，写出正确的 `.trackName`、`.artistName` 取值路径 |
| **DOM 操作** | 用 `innerHTML` 动态渲染搜索结果列表 | 你能用 `map().join()` 批量生成 HTML 并一次性插入 DOM |
| **状态管理** | 五种状态（IDLE/LOADING/SUCCESS/EMPTY/ERROR）的完整 UI 覆盖 | 你能在下一个项目中，动手之前就列出所有可能的状态 |
| **竞态条件处理** | 用 requestId 计数器防止旧请求覆盖新结果 | 你能举出一个场景说明竞态条件为什么会发生，以及如何解决 |

### 软技能（思维方式和工作习惯）

| 思维模式 | 在项目中的体现 |
|---------|---------------|
| **先调研，再动手** | 步骤 2 中先在浏览器测试 API，搞清楚返回结构再写代码 |
| **先跑通，再跑好** | 步骤 3 用按钮触发搜索跑通基本流程，步骤 4 再加防抖优化，步骤 5 再加状态管理 |
| **考虑边界情况** | 不仅考虑"正常搜到结果"，还考虑"搜不到""网络断""输入为空""旧请求覆盖新结果" |
| **单一职责** | `searchMusic` 只负责请求，`renderByStatus` 只负责渲染，`doSearch` 只负责协调 |
| **防御性编程** | `switch` 有 `default` 分支、状态用常量而非字符串、渲染前检查数据是否存在 |

## 这个项目证明你能做什么

当你在简历上写下"音乐搜索器"项目，或者在面试中被问到"你做过什么前端项目"时，你可以这样说：

---

**30 秒版本（电梯演讲）：**

我用原生 JavaScript 做了一个音乐搜索器，对接了 Apple iTunes 的公开 API。用户输入关键词后，页面自动通过防抖机制发送异步请求，并展示搜索结果。我处理了五种 UI 状态（空闲、加载中、成功、无结果、错误），并且用请求计数器解决了异步竞态条件问题。

---

**3 分钟版本（面试详细回答）：**

这个项目是一个实时音乐搜索应用，技术栈是原生 HTML + CSS + JavaScript，没有用任何框架。

**数据来源**是 iTunes Search API——一个免费的 RESTful 接口。我首先在浏览器中直接测试了 API，搞清楚了它接受什么参数、返回什么数据结构。

**核心功能**是搜索即输入——用户在输入框中打字，不需要点击按钮，停止输入 400 毫秒后自动触发搜索。这是通过自己实现防抖函数做到的：用 `setTimeout` 延迟执行，用 `clearTimeout` 取消上一次的未执行任务。

**状态管理**是我在这个项目中最关注的部分。我定义了五种状态：空闲（刚打开页面）、加载中（请求进行中）、成功（有结果）、空结果（搜不到）、错误（网络故障）。每种状态都有对应的 UI 反馈——加载动画、空结果提示、错误提示加重试按钮。这样做的好处是，用户在任何情况下都知道发生了什么，不会面对空白页面不知所措。

**技术难点**是异步竞态条件的处理。场景是用户快速输入不同关键词时，后发的请求可能比先发的请求先返回，导致旧结果覆盖新结果。我用了一个递增的请求 ID 计数器——每次发请求时 ID 自增并存入闭包，请求回来后检查 ID 是否还是最新的，不是就丢弃结果。这是在前端不依赖框架处理异步竞态条件的一次实践。

整个项目让我把 Promise、async/await、fetch、防抖、状态管理这些零散的知识点串成了一个完整的功能闭环。

## 如何向面试官展开讨论

如果面试官追问，你可以从以下几个方向展开：

**问："为什么不用 React/Vue 做这个项目？"**
答："这个项目是为了深入理解原生 JavaScript 的异步机制。用框架的话，`useEffect` 或 `watch` 会帮我处理很多细节，我反而看不到底层发生了什么。现在我用原生 JS 做完之后，再去学 Vue 时对 Vue 的响应式系统理解更深——因为我知道它帮我省了什么。"

**问："防抖和节流有什么区别？为什么这里用防抖而不是节流？"**
答："防抖是'连续操作结束后执行一次'，节流是'固定时间间隔执行一次'。搜索场景中，用户关心的不是'输入过程中的中间结果'，而是'输入结束后的最终关键词'，所以用防抖。节流更适合滚动加载、窗口 resize 这种需要持续反馈的场景。"

**问："如果 API 挂了怎么办？"**
答："我在 catch 块中捕获了异常，切换到 ERROR 状态，给用户展示错误提示和重试按钮。在生产环境中，我还可以加指数退避重试——第一次失败等 1 秒重试，第二次等 2 秒，第三次等 4 秒。另外可以加一个降级方案：缓存上次成功的搜索结果，在 API 不可用时展示缓存数据。"

**问："有没有考虑过安全问题？"**
答："主要关注两点：一是用 `innerHTML` 渲染用户输入的内容时，需要确保 iTunes API 返回的数据不会包含恶意脚本（iTunes API 是受信任的 Apple 服务，风险较低）。如果未来扩展到允许用户自定义标签或评论，就需要对内容做转义。二是通过 HTTPS 发送所有请求，防止中间人攻击。"

## 你可以迁移到下一个项目的经验

1. **API 调研流程**：浏览器先测 -> 理解返回结构 -> 再写代码。这个流程适用于任何需要对接第三方接口的项目。
2. **状态优先于 UI**：在写 HTML/CSS 之前，先列出所有可能的状态。这个习惯在 React/Vue 项目中同样适用。
3. **防抖是搜索标配**：无论是原生 JS、React、Vue，还是小程序，搜索框都需要防抖。
4. **竞态条件是异步编程的常态**：不仅是搜索框，任何"连续异步操作"的场景（分页加载、自动保存、实时过滤）都需要处理竞态条件。
