# 步骤 6：代码回顾 —— 从全局视角理解你的作品

## 架构分析：你的代码做了哪些分层

回顾 `app.js` 的结构，你实际上（无意识地）做了分层：

```
┌──────────────────────────────────────┐
│  事件层 (Event Layer)                │
│  - addEventListener('input', ...)    │  "用户做了什么"
│  - debounce 包装                      │
├──────────────────────────────────────┤
│  控制层 (Controller Layer)           │
│  - doSearch()                        │  "什么时候做什么"
│  - 状态切换逻辑                       │
│  - 竞态条件检查                       │
├──────────────────────────────────────┤
│  服务层 (Service Layer)              │
│  - searchMusic()                     │  "数据从哪来"
│  - fetch + JSON 解析                 │
│  - URL 构建                          │
├──────────────────────────────────────┤
│  视图层 (View Layer)                 │
│  - renderByStatus()                  │  "数据怎么展示"
│  - switch 五种状态                   │
└──────────────────────────────────────┘
```

这个分层虽然简单，但它就是 MVC 模式的雏形。后面学到 Vue/React 时，你会发现框架本质上就是在帮你规范化这种分层。

## 技术决策回顾：在每个节点你做了什么选择

| 决策点 | 你选择了 | 备选方案 | 为什么你的选择是对的 |
|--------|---------|---------|---------------------|
| 搜索触发方式 | 输入即搜 + 防抖 | 按钮点击 | 用户体验更好，符合主流产品习惯 |
| 防抖延迟 | 400ms | 300ms（太灵敏）、800ms（太迟钝） | 400ms 是搜索场景的经验值，兼顾灵敏和性能 |
| 状态管理方式 | Status 对象 + switch | if/else 散落各处 | 集中管理，不会漏处理某个状态 |
| 竞态条件处理 | requestId 计数器 | AbortController | 计数器更直观，AbortController 更好（见下文改进建议） |
| 错误恢复 | 重试按钮 | 自动重试 | 让用户主动决策，避免自动重试浪费请求 |
| DOM 更新方式 | innerHTML 一次写入 | 逐条 appendChild | 性能更好，减少回流次数 |

## 可以改进的地方（诚实面对）

一个诚实的 Code Review 不仅说好的，也指出来哪里还可以更好。以下是本项目的改进点——你可以选择现在做，也可以在后续项目中实践（尤其是 Vue 版本）：

### 改进 1：用 AbortController 替代 requestId 计数器处理竞态条件

当前的 `requestId` 方案虽然有效，但**旧请求实际上还在网络上传输，只是结果被丢弃了**。更好的做法是用 `AbortController` 直接取消旧请求，节省带宽：

```js
let abortController = null  // 保存当前的取消控制器

async function searchMusic(term) {
  // 如果有正在进行的请求，取消它
  if (abortController) {
    abortController.abort()  // 取消旧请求，触发 fetch 抛出 AbortError
  }

  // 创建新的取消控制器
  abortController = new AbortController()

  const url = `https://itunes.apple.com/search?term=${encodeURIComponent(term)}&limit=20&country=cn`

  // 把 signal 传给 fetch
  const response = await fetch(url, { signal: abortController.signal })

  if (!response.ok) {
    throw new Error(`搜索失败：HTTP ${response.status}`)
  }

  const data = await response.json()
  return data.results
}
```

> 注意：`AbortController` 取消请求后，`fetch` 会抛出一个 `AbortError`，需要在 catch 中区分它是"用户取消的"还是"真正的网络错误"。

### 改进 2：搜索结果没有数量标识

当前 SUCCESS 状态下，用户不知道搜到了多少条结果。可以加一句：

```js
// 在 renderByStatus 的 SUCCESS 分支中，先插入一个统计行
let html = `<p style="color:#999; margin-bottom:12px;">共找到 ${data.length} 首歌曲</p>`
html += data.map(track => `...`).join('')
resultsDiv.innerHTML = html
```

### 改进 3：没有对搜索结果进行去重或排序

iTunes API 返回的结果可能有重复的歌曲（同一首歌在不同专辑中）。你可以：

```js
// 在 renderResults 前，按 trackId 去重
const uniqueResults = results.filter(
  (track, index, arr) => arr.findIndex(t => t.trackId === track.trackId) === index
)
```

### 改进 4：移动端没有做适配

当前设计在 PC 上看起来很舒服，但在手机上可能有问题。可以加媒体查询：

```css
@media (max-width: 480px) {
  body {
    padding: 0 12px;
  }
  .result-item {
    flex-direction: column;  /* 手机上图片在上面，文字在下面 */
    text-align: center;
  }
}
```

### 改进 5：缺少键盘导航和无障碍支持

- 搜索结果列表不支持键盘上下选择
- 图片没有有意义的 `alt` 文本（当前是 "xxx 封面"，对屏幕阅读器用户帮助有限）
