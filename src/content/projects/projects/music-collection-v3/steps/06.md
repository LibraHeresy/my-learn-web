# 第 6 步：GitHub Actions 自动部署

## 你要做什么

设置 GitHub Actions，实现 "push 代码 → 自动构建 → 自动部署" 的完整自动化流程。从此以后改代码只需 `git push`，其余全部自动完成。

## 为什么这一步重要

第 5 步的手动部署可用，但每次改代码都要记得跑 `npm run build && npm run deploy`——忘了跑的话，线上版本就不会更新。GitHub Actions 把这件事自动化了：你 push 代码，GitHub 的服务器会自动帮你构建、部署。这是现代前端开发的标配流程，也是 CI/CD（持续集成/持续部署）的最基本形式。

## 动手操作

### 1. 理解我们要做什么

在操作之前，先在脑子里过一遍整个自动化流程：

```
你本地 git push → GitHub 仓库的 main 分支有了新代码
    ↓
GitHub Actions 检测到 main 分支有 push
    ↓
自动启动一台虚拟机（Ubuntu Linux）
    ↓
在虚拟机上：npm ci（安装依赖）
    ↓
在虚拟机上：npm run build（构建）
    ↓
在虚拟机上：把 dist/ 部署到 GitHub Pages
    ↓
完成！线上版本自动更新
```

你只需要做一次配置，之后每次 push 都会自动走完这个流程。

### 2. 创建 Workflow 文件

GitHub Actions 的配置是 YAML 文件，放在项目中的 `.github/workflows/` 目录下。文件名任意，GitHub 会自动扫描这个目录。

**操作步骤**：

1. 在项目根目录新建文件夹 `.github`（注意前面有个点）
2. 在 `.github` 文件夹中新建文件夹 `workflows`
3. 在 `workflows` 文件夹中新建文件 `deploy.yml`

最终路径：`.github/workflows/deploy.yml`

### 3. 编写 Workflow 配置

将以下内容写入 `deploy.yml`：

```yaml
# Workflow 的名称（会显示在 GitHub 仓库的 Actions 页面）
name: Deploy to GitHub Pages

# 触发条件：当 main 分支有 push 时自动运行
on:
  push:
    branches: [main]

# 授予 Workflow 写入 GitHub Pages 的权限
permissions:
  contents: read
  pages: write
  id-token: write

# 一个 workflow 包含一个或多个 job（任务）
# 这里只有一个 job：build-and-deploy
jobs:
  build-and-deploy:
    # 运行环境：GitHub 提供的最新 Ubuntu 虚拟机
    runs-on: ubuntu-latest

    # 关联 GitHub Pages 环境（部署后可以拿到线上 URL）
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    # 步骤列表：一个 job 包含多个 step（步骤），按顺序执行
    steps:
      # 步骤 1：把仓库代码下载到虚拟机
      - name: Checkout code
        uses: actions/checkout@v4

      # 步骤 2：在虚拟机中安装 Node.js
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 18

      # 步骤 3：安装项目依赖
      - name: Install dependencies
        run: npm ci

      # 步骤 4：构建生产版本
      - name: Build
        run: npm run build

      # 步骤 5：配置 GitHub Pages
      - name: Setup Pages
        uses: actions/configure-pages@v4

      # 步骤 6：把 dist/ 打包为部署工件
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist

      # 步骤 7：部署工件到 GitHub Pages
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

### 逐行解释（重要——理解每行在做什么）

**name: Deploy to GitHub Pages** —— 这个 workflow 的名称。在 GitHub 仓库的 Actions 标签页中会显示这个名字。

**on.push.branches: [main]** —— 触发条件。意思是：当有人向 `main` 分支推送代码时，自动运行这个 workflow。如果你 push 到其他分支（比如 `feature/xxx`），不会触发。

**permissions** —— 给这个 workflow 授权：
- `contents: read`：可以读取仓库代码（用来 checkout）
- `pages: write`：可以向 GitHub Pages 写入内容（用来部署）
- `id-token: write`：可以获取临时身份令牌（GitHub Pages 部署需要）

**runs-on: ubuntu-latest** —— GitHub 会启动一台全新的 Ubuntu Linux 虚拟机来运行你的 workflow。这台虚拟机是临时的——任务结束后自动销毁。它预装了 Node.js、npm、git 等常用工具。

**environment** —— 关联到 GitHub Pages 环境。部署完成后，GitHub 会把部署后的 URL 自动填入 `steps.deployment.outputs.page_url`。

**uses: actions/checkout@v4** —— `uses` 表示使用一个"Action"（别人写好的可复用步骤）。`actions/checkout@v4` 是 GitHub 官方提供的 Action，作用是把你的仓库代码下载到虚拟机的当前工作目录。`v4` 是版本号。

**uses: actions/setup-node@v4** + `with: node-version: 18` —— 安装 Node.js 18.x。注意这里用的是 `node-version: 18`，不是 `node-version: 18.x`——数字类型不需要引号。

**run: npm ci** —— `run` 表示直接在虚拟机的终端中执行命令。`npm ci` 和 `npm install` 的区别：
- `npm install`：读取 `package.json`，安装依赖，可能更新 `package-lock.json`
- `npm ci`：严格按照 `package-lock.json` 安装——更快、更确定（每次安装结果完全一致）
- 在 CI/CD 环境中应始终使用 `npm ci`

**run: npm run build** —— 执行构建命令。注意：`vite.config.js` 中的 `base: '/music-collection/'` 配置会被正确使用，构建产物中的资源路径正确。

**uses: actions/configure-pages@v4** —— 自动配置 GitHub Pages 的相关设置（不需要你手动去 Settings 里改）。

**uses: actions/upload-pages-artifact@v3** + `with: path: ./dist` —— 把 `dist/` 文件夹的内容打包上传，作为"部署工件"（artifact）。这个工件会被传递给下一步的部署 Action。

**uses: actions/deploy-pages@v4** —— 把上一步上传的工件部署到 GitHub Pages。`id: deployment` 给这一步起了个 ID，方便前面的 `environment.url` 引用。

### 4. 推送并观察自动化

保存 `deploy.yml` 后，提交并推送：

```bash
git add .github/
git commit -m "添加 GitHub Actions 自动部署配置"
git push
```

推送完成后：

1. 打开 GitHub 仓库页面
2. 点击顶部的 **Actions** 标签
3. 你会看到一个正在运行（黄色旋转图标）的 workflow，名字是 "添加 GitHub Actions 自动部署配置"（commit message）
4. 点击这条记录，你会看到各个步骤的执行状态——点击 "build-and-deploy" 可以展开看到每个步骤的日志
5. 等待所有步骤完成（全部变成绿色对勾，大约 1-2 分钟）

**注意**：第一次运行时，需要在仓库 Settings → Pages → Source 中选择 **"GitHub Actions"**（不再是 `gh-pages` 分支）。GitHub Actions 的部署会作为新的 Pages 来源。

如果 Actions 运行成功但线上页面没更新：
1. 去 Settings → Pages
2. 在 "Build and deployment" → "Source" 中选择 **"GitHub Actions"**
3. 保存后，下一次 push 会自动触发正确的部署

### 5. 验证自动化

修改一个明显的内容（比如把 `App.vue` 中的标题 `🎵 我的音乐收藏` 改成 `🎵 我的音乐收藏 v2.0`）：

```bash
# 修改 src/App.vue 中的标题文字后
git add .
git commit -m "测试自动部署：更新标题"
git push
```

然后：
1. 打开仓库的 Actions 页面，会看到一个新的 workflow 正在运行
2. 等它跑完（绿色对勾）
3. 刷新你的 GitHub Pages 网址，标题应该自动更新了

**从此以后，你的部署流程只需要一步**：`git push`。

### 6. 比较手动部署和自动部署

| | 手动部署（第 5 步） | 自动部署（第 6 步） |
|---|---|---|
| 步骤 | `npm run build` → `npm run deploy`（手动执行 2 条命令） | `git push`（1 条命令） |
| 忘记部署 | 线上版本落后于代码 | 不存在这个问题——push 即部署 |
| 依赖 | 依赖本地环境（Node 版本等） | 在标准化的虚拟机中执行，环境一致 |
| 部署记录 | 无 | 每次部署的日志永久保存在 Actions 中 |
| 团队协作 | 谁来部署？可能冲突 | 谁 push 谁触发——不会冲突 |

## 预期结果

- 推送代码后，GitHub Actions 自动运行，完成构建和部署
- 几分钟后，线上版本自动更新为最新代码
- Actions 页面能看到完整的运行日志

## 常见错误

- **错误**：`.github/workflows/deploy.yml` 的缩进不对。**后果**：YAML 对缩进非常敏感——必须用空格（不能用 Tab），且缩进层级必须一致（通常 2 个空格一级）。如果缩进错了，GitHub 会提示 "Invalid workflow file"。**解决**：复制上面的配置时确保缩进完全一致。VS Code 右下角可以看到当前文件的缩进设置，确保是空格而非 Tab。
- **错误**：workflow 运行失败，日志中显示 `npm ci` 报错。**原因**：可能是 `package-lock.json` 文件有问题或没有被提交到 Git。**解决**：确认 `package-lock.json` 在 Git 中（`git status` 检查），而且没有出现在 `.gitignore` 中。
- **错误**：workflow 成功但线上页面还是旧版本。**原因 1**：Settings → Pages 的 Source 没切换到 "GitHub Actions"。**原因 2**：浏览器缓存了旧版本——按 `Ctrl+Shift+R`（Windows）或 `Cmd+Shift+R`（Mac）强制刷新。
- **错误**：workflow 的日志中 `npm run build` 失败，报错说找不到某个文件或模块。**原因**：本地能跑但 CI 环境中不行——通常是文件路径大小写问题。Windows 不区分大小写（`App.vue` 和 `app.vue` 一样），但 CI 的 Linux 系统区分大小写。**解决**：确保所有 import 路径的大小写和实际文件完全一致。
