# 第 1 步：什么是"工程化"？

## 你要做什么

理解前端工程化的四个核心环节——Git、GitHub、构建、部署——以及它们各自解决什么问题。建立从"写完代码"到"产品上线"的完整心智模型。

## 为什么这一步重要

v2 结束时你的项目只能在自己的电脑上运行。要让别人也能看到你的作品，必须走完工程化流程。这不只是"学几个工具"——这是从"写给自己看的学习笔记"到"交付给用户的真实产品"的转变。理解每个环节的意义，后面实际操作时才不会觉得"在跑一堆莫名其妙的命令"。

## 工程化的四个环节

### 环节一：Git（版本管理）

**它解决什么问题**：你写完一个功能，改了几行代码，过两天又想改回来——但你已经不记得原来是什么样的了。

**Git 做什么**：给你的项目拍"快照"。每当你完成一个小目标（比如"添加了筛选功能"），你就拍一张快照（`git commit`）。之后你可以随时回溯到任何一张快照，查看改了哪些文件、哪一行变了。

**类比**：就像游戏的存档。打 Boss 之前存个档——死了可以读档重来。Git 的每个 commit 就是一次存档，而且所有存档都保留着，你可以跳到任何一个存档点。

**关键术语**：
- **仓库（repository）**：一个项目的所有快照的集合
- **提交（commit）**：一次快照，记录了你改了哪些文件
- **暂存区（stage）**：你"选中"哪些文件的改动要放进下一次 commit

### 环节二：GitHub（远程仓库 + 协作）

**它解决什么问题**：你的代码只在你电脑上。电脑坏了代码就没了。你想把项目链接发给朋友，但总不能让人家装个 VS Code 来你电脑上看。

**GitHub 做什么**：把你的 Git 仓库"推"到一个公开的网站上。你的代码有了一个网上备份（电脑坏了不怕），也有了一个公开的网址（别人可以浏览、下载、甚至给你提建议）。

**类比**：Git 是你的本地相册，GitHub 是你发到朋友圈的照片——从私密变公开，从本地变云端。

**关键术语**：
- **远程仓库（remote）**：GitHub 上的那个仓库
- **推送（push）**：把本地的 commit 同步到 GitHub
- **克隆（clone）**：把 GitHub 上的项目下载到本地
- **Pull Request（PR）**：请求别人审阅并合并你的代码改动

### 环节三：构建（Build）

**它解决什么问题**：你开发时用的 Vue 项目（有热更新、有源码、有注释、文件很多）不能直接部署——太大了，加载慢，而且包含开发专用的代码。

**构建做什么**：把你写的源码"打包"成一堆优化过的、用户真正需要的文件——变量名缩短、空格删除、多文件合并、代码压缩。结果是 `dist/` 文件夹，里面的内容就是给用户访问的。

**类比**：开发版本是"厨房里的食材和锅碗瓢盆"（你能看懂，但食客不能直接端上桌），构建是"做好的菜"（摆盘精美，食客直接吃）。

**关键术语**：
- **生产版本 / production build**：构建后的最终产物
- **压缩（minify）**：删除空格、缩短变量名来减小文件体积
- **打包（bundle）**：把多个 JS/文件合并成一个文件

### 环节四：部署（Deploy）

**它解决什么问题**：你的 `dist/` 文件夹在本地，别人访问不到。

**部署做什么**：把构建产物上传到一台**能被公开访问的服务器**上。GitHub Pages 是 GitHub 提供的免费静态网站托管服务——你可以把 `dist/` 的内容推上去，获得一个 `https://你的用户名.github.io/项目名/` 的网址。

**类比**：构建是做好菜，部署是端到餐桌上——食客终于能吃到了。

**关键术语**：
- **静态网站托管**：托管不需要后端服务器的网站（纯 HTML/CSS/JS）
- **GitHub Pages**：GitHub 的免费静态托管服务
- **CI/CD**：持续集成/持续部署，自动化构建和部署的流程

## 完整链路：从代码到线上

```
你写代码 → git commit（存档）→ git push（上传到 GitHub）
                                        ↓
                               GitHub Actions 监听到 push
                                        ↓
                               自动 npm run build（构建）
                                        ↓
                               自动部署到 GitHub Pages（上线）
                                        ↓
                               用户通过网址访问你的应用
```

**你最终得到什么**：
1. 本地有一套可以随时修改的源码
2. GitHub 上有一个公开的代码仓库（程序员的"技术名片"）
3. 一个固定的网址，任何人都可以访问你的音乐收藏应用
4. 以后你改代码 → `git push` → 自动更新线上版本（不需要手动部署）

## 前提条件

在开始之前，确认：

1. v2 项目已经完成，在本地可以正常运行（`npm run dev`）
2. 有一个 GitHub 账号（没有的话去 [github.com](https://github.com) 注册，免费，2 分钟搞定）
3. 电脑上安装了 Git（打开终端输入 `git --version`，如果能输出版本号就是装好了）

**验证环境**：打开终端，依次运行：

```bash
git --version    # 应该输出类似 git version 2.4x.x
node -v          # 应该输出 v18.x 或 v20.x
npm -v           # 应该输出 9.x 或 10.x
```

如果 `git --version` 没有输出版本号，你需要先安装 Git：
- 访问 https://git-scm.com/downloads
- 下载对应你操作系统的版本（Windows / macOS）
- 安装时一路点"下一步"，所有选项保持默认即可（不用改任何设置）
- 安装完成后**关闭并重新打开终端**，再运行 `git --version`

## 预期结果

读完这一步，你不需要操作任何东西。你只需要理解：
1. Git = 本地版本存档
2. GitHub = 云端代码仓库（公开网址）
3. Build = 把源码打包成给用户用的优化版本
4. Deploy = 把打包结果放到服务器上让人访问
5. 这四个环节串起来就是一个完整的"开发 → 交付"流程

## 常见错误

- **错误**：以为"部署就是把源码文件夹复制到服务器上"。**后果**：用户访问时加载的是未构建的开发版本——文件体积大、加载慢、有 Vue 开发模式的额外开销。**解决**：部署前必须先 `npm run build`，部署的是 `dist/` 文件夹，不是整个项目。
- **错误**：以为 Git 和 GitHub 是一回事。**后果**：不理解"本地仓库"和"远程仓库"的关系，后面推代码时容易搞混。**解决**：Git 是工具（在你的电脑上运行），GitHub 是网站（托管你的仓库）。你可以在没有网络的情况下使用 Git（commit 和查看历史），但 push 需要联网。
- **错误**：跳过这一步直接去操作 Git 命令。**后果**：拿到命令就敲，不理解每一步在干什么，出了错不知道从哪查。**解决**：确保理解了四个环节的关系再继续。
