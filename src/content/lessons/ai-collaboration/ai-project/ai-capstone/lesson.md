# 完整项目：从 Prompt 到产品

:::analogy
这是一次长途自驾——AI 是你的导航和定速巡航，但方向盘在你手里。从选目的地到到达终点，每一个导航建议你都判断要不要听。等你到了，你会发现这段路上你学会的不是"怎么用导航"，而是"怎么开好车"。

:::

:::prerequisite
你已经完成了本课程前面所有的章节——HTML、CSS、JS、Vue、AI 协作。你现在有独立完成一个完整前端项目所需的所有技能，以及最重要的：判断 AI 输出是否正确的能力。

:::

:::explain{title="一、你的最后挑战"}
从下面三个项目中选择一个（或提出你自己的项目想法），用 AI 全程协助，从想法到能演示的产品，独立完成。

**选项 A：学习备忘录（Music Memo）**
记录学习灵感的单页应用。用户可以写下一段学习笔记——内容、心情标签、学习时间、所属科目——保存到列表，可以编辑、删除、搜索。数据存到 localStorage。

**选项 B：番茄钟计时器（Pomodoro Timer）**
为学习者设计的专注计时工具。设置多个专注段（如"阅读 25 分钟""写作 20 分钟""休息 5 分钟"），按顺序计时，每段结束浏览器通知。可以保存常用的专注计划。

**选项 C：知识卡片浏览器（Flashcard Browser）**
搜索和浏览知识卡片的单页应用。使用本地模拟数据（JSON 文件）。卡片包含标题、分类、内容摘要、难度等级。可以按分类筛选、按难度排序、搜索标题和内容。

选好后，用你在本课程中学到的所有方法：规划（第 9 课）、脚手架（第 10 课）、组件生成与整合（第 11 课）、调试（第 8 课）。每一步都由你做最终决定。
:::

:::explain{title="二、你的项目日记"}
在整个开发过程中，每天（或每完成一个重要阶段）写一段简短的日记。不需要格式，不需要文采——只需要记录：

1. **今天让 AI 做了什么？** 生成什么代码、解决什么问题、解释什么东西。
2. **AI 的输出对吗？** 如果对，为什么对？如果不对，你做了什么调整？
3. **我今天学到了什么？** 不是"我知道了某个 API"，而是"我理解了一个概念"或"我发现了一个规律"。

### 日记示例

```
Day 1：让 AI 做了项目规划。它列出了 15 个功能——太多了。
我砍掉了用户系统、数据导出、统计图表，只保留核心的 5 个功能。
学到：AI 的规划需要我大刀阔斧地砍，不能全盘接受。

Day 2：AI 帮我搭了 Vite + Vue 3 脚手架。过程顺利——npm create vite 我本来就会，AI 只是省了我清默认文件的时间。
学到：AI 在手熟的事情上帮我加速，在手生的事情上需要我辨别。

Day 3：生成 TimerDisplay 组件。AI 第一版代码没问题，但我发现它没有处理 props 为 0 时显示 00:00 的格式化。我加上了格式化函数。AI 写了 80% 的代码，我写了 20% 的关键细节。
学到：AI 生成代码很快，但"关键细节"——边界处理、格式转换、用户体验——还是我的事。

Day 5：出 bug——切换页面后计时器还在跑，控制台报错"setInterval is not cleared"。贴给 AI，它帮我找到了原因：onUnmounted 里没有 cleanup。修复很简单：if (timer) clearInterval(timer)。但我理解了这个 bug 的根因：Vue 组件销毁时，你在 setup 里创建的任何外部资源（定时器、事件监听、请求）都必须手动清理。这是一条我以后永远不会忘记的原则。
学到：每个修好的 bug 如果理解了根因，等于掌握了一条设计原则。不是因为 AI 修得好，是因为我追问了为什么。

Day 7：项目完成。核心功能全部跑通，没有已知 bug。回头看，AI 帮我写了大约 60% 的代码量，但剩下的 40%——设计决策、接口定义、边界处理、bug 修复、视觉调优——全是我做的。而这 40% 花费了我 80% 的时间。AI 省掉的是最机械的代码量，留下的是最有价值的思考和判断。
学到：AI 是效率工具，不是替代品。我用 AI 完成了一个一周前我觉得自己一个人做不完的项目——不是因为 AI 替代了我的能力，是因为 AI 放大了我的能力。
```

**写日记的目的不是记录，是反思**

写完日记后重读一遍，你会发现一个规律：你在日记里记的"我学会了"，远多于"AI 生成了"。AI 帮你生成了代码，但真正的成长发生在你审查代码、做决策、修 bug、追问为什么的时候。AI 是加速器——但你才是发动机。
:::

:::explain{title="三、做完后回答的三个问题"}
项目跑起来后，认真回答这三个问题。写下你的答案，不要只在心里想。

### 问题 1：AI 在哪件事上帮你最多？

是你的弱项还是强项？（比如你 CSS 一直不太自信，AI 帮你处理了大部分样式——省了你很多痛苦。又比如你 JS 逻辑很强，AI 的 JS 代码你基本都要改一遍——省了什么呢？好像不多。）

这个问题的答案会让你理解：**AI 作为工具，它的实际价值高度依赖使用者。** 你不擅长的地方它确实能兜底，但只有在你擅长的地方（你能辨别好坏），AI 的输出才真正提升了质量。

### 问题 2：AI 在哪件事上最让你失望？

是一个具体的 bug？一个错误的设计建议？还是一次反复交流也没解决好的功能？为什么这个问题 AI 解决不好？它需要什么信息才能解决——而这些信息 AI 根本得不到？

这个问题会让你理解 AI 的盲区。不是"AI 不行"，而是"这个任务需要的信息不在 AI 的训练数据里，也不在你给它的上下文中"。

### 问题 3：下次和 AI 协作，你会做什么不同的事？

Prompt 的写法？验证的频率？对 AI 输出的信任度？砍掉 AI 过度设计的力度？迭代的节奏？

这个问题是你从"会用 AI"到"善用 AI"的转折点。答案没有对错——但认真思考过这个问题的人，和没思考过的人，在一个月后的 AI 协作效率会有本质差距。

**一个过来人的三个回答（示例）**

1. AI 帮我最多的是 CSS 和样式调优。我对颜色、间距这些不够敏感，AI 帮我处理基础样式，我的精力放在组件逻辑上——我们互补了。
2. AI 最让我失望的是它不理解"简单"。我让它写一个简单的 localStorage 封装，它写了一个带序列化校验、版本管理、60 行代码的"小工具"。我其实只需要 getItem 和 setItem 两个函数。我发现 AI 的默认倾向是"做多"而不是"做少"——这个倾向你必须主动纠正。
3. 下次我会更早地、更频繁地跑实际页面验证。这次我有一段 CSS 在 AI 对话里看没问题，但放浏览器里间距完全不对。我应该在每轮对话后立刻刷新页面看效果，而不是攒 5 轮修改一起看。
:::

:::explain{title="四、从完成到展示"}
项目做完了，别人怎么知道你做出了东西？做这两件事：

1. **把项目部署到线上。** 用 GitHub Pages、Vercel 或 Netlify 部署你的项目。把部署过程告诉 AI："我用 Vite + Vue 3 做了一个项目，帮我生成 Vercel 部署的步骤。"AI 会给你指令，你按步骤操作。部署完成后，给 3 个朋友发链接，让他们用手机打开——"帮我测一下，有任何问题截图给我。"

2. **写一段 200 字的项目说明。** 不需要花哨——说清楚：这是什么项目、解决了什么问题（即使是"帮我专注学习"也是问题）、用了什么技术、你独立完成了什么（"在 AI 辅助下独立完成"是一个值得自豪的表述）。

这两件事的意义：你从一个"学习前端的人"变成了一个"做出了东西的前端开发者"。这两者的区别，不在于你知道多少知识——在于有没有一个能跑、能看、能给人演示的东西，证明你把知识转化成了产品。

:::

:::task{title="结业项目验收"}
::::step{id="1"}
完成你的结业项目。核心功能全部跑通，无已知严重 bug。自己从头到尾操作一遍核心流程，确认流畅。
::::
::::step{id="2"}
写项目日记（至少 3 条，对应项目的开始、中间、结束）。每条包含：做了什么、AI 帮了什么、我学了什么。
::::
::::step{id="3"}
回答三个问题（写下来）。每个回答至少 3 句话，有具体的场景和反思，不要只写"AI 帮了很多"这种空话。
::::
::::step{id="4"}
部署你的项目到线上（GitHub Pages / Vercel / Netlify 任选），把链接发给至少 2 个人，收集他们的反馈。记录一条你收到的最有价值的反馈。
::::
:::


:::recap
你一个人，一台电脑，一个 AI 助手——从想法到能演示的产品，完成了整个流程。AI 帮你写了大约 60% 的代码量，但你花了 80% 的时间在剩下 40% 的事情上——设计决策、接口定义、边界处理、bug 修复、视觉调优。这 40% 就是你在 AI 时代不可替代的价值。写项目日记、回答三个反思问题、把项目部署上线给别人用——这三件事把你从"学习前端的人"变成了"做出了东西的前端开发者"。

:::
