# 用 AI 做项目规划

:::analogy
AI 是那种会给你列出 50 个功能的规划狂同事。你的任务是拿一支红笔，划掉 40 个，保留 10 个最重要的——然后说："我们只做这 10 个，两周内交付。"

:::

:::prerequisite
你有一个想做的前端项目想法——不需要完美，有模糊的方向就够。可以是个人博客、番茄钟、记账本、作品集网站——任何你能用 Vue + Vite 实现的东西。

:::

:::explain{title="一、你的问题"}
你想做一个项目，脑子里有一个模糊的想法，但不知道从哪里开始。你让 AI 帮你做项目规划，它给你列了 30 个功能、8 个技术栈、50 个开发步骤。你看完只有一个感觉：我做不完。问题不在你——在 AI 的规划没有"范围"这个概念。你需要的是"我能在一周内完成的规划"，而不是"一个 10 人团队 3 个月能做的规划"。
:::

:::explain{title="二、解决方案：三刀砍出可行范围"}
让 AI 帮你做规划的正确姿势，不是"AI 给什么就做什么"，而是"AI 把选项铺开，你来砍掉不需要的"。

### 第 1 刀：砍功能——只保留核心体验

假设你要做一个"番茄钟"应用。AI 的规划可能包含：
- 设置计时、开始暂停、到时间提醒（核心）
- 用户注册登录、云端同步、统计图表、社交分享、自定义主题、桌面通知、PWA 离线支持、多语言国际化（附加）

问自己一个问题：**"如果这个应用只能做一件事，是哪件？"** 答案是"计时并提醒"。那么：
- 必须做：计时器、设置时间、提醒通知
- 可做可不做（砍掉）：统计图表、社交功能、多语言
- 以后再说（砍掉）：用户系统、云端同步、PWA

砍的标准不是"这个功能好不好"，而是"没有这个功能，核心体验还在不在"。

**砍功能的量化标准**

如果你的可用时间是 7 天（每天 2-3 小时），你最多能做 4-6 个功能。AI 列出 30 个功能——你需要划掉 24 个。做减法不是妥协，是做项目的常识。一个只有 5 个功能但每个都跑得稳的产品，比一个 25 个功能但每个都有 bug 的产品好一百倍。

### 第 2 刀：砍技术栈——只用你会的

AI 可能建议：TypeScript + Pinia + Vue Router + Tailwind CSS + Vitest + Playwright + Docker。

问自己："我现在能熟练使用哪些技术？" 如果你只学了 Vue 3 + 原生 CSS，那就只用这两个。技术栈配置不是"多就是好"——是"每多一个你不熟悉的技术，项目失败的概率就翻一倍"。

告诉 AI："我只会 Vue 3 + 原生 CSS + localStorage。不要推荐超出这个范围的技术。"这会让 AI 的规划从"理想架构"变成"可执行方案"。

### 第 3 刀：砍步骤——按依赖关系重排

AI 列出的开发步骤可能顺序不对。比如"先做好登录页面再做番茄钟功能"——这是典型的优先级颠倒。

正确顺序应该按依赖关系排：
1. 项目脚手架（Vite + Vue 3 初始化）
2. 核心功能（计时器逻辑——其他所有功能都依赖它）
3. 核心 UI（计时器显示 + 控制按钮——能用了再说）
4. 辅助功能（设置面板、提醒声音、预设任务）
5. 打磨（动画优化、响应式适配、错误处理）

你的工作不是接受 AI 的排序，而是**根据你写的组件之间的依赖关系，重新排序。** 哪个组件被其他组件调用——先做。哪个组件独立——后做。

**实战：一个番茄钟的规划对话**

```
你的 Prompt：
我正在做一个番茄钟 Web 应用，技术栈只使用 Vue 3 + 原生 CSS + localStorage。
我的可用时间是 5 天（每天 2 小时）。
帮我做项目规划：
1. 列出所有可能的功能
2. 帮我区分：核心功能（必须做）、加分功能（有时间再做）、不做功能（本次不做）
3. 用 Vue 3 Composition API 拆分成组件树
4. 设计数据流：哪些数据用 ref 在组件内管理，哪些需要提升到 App.vue
5. 按依赖关系排开发步骤，每步标注预计用时

注意：我不需要用户系统、不需要后端、不需要数据库。
```

AI 会给出一个详细的规划。然后你做三件事：
1. 红色：划掉所有"加分功能"和"不做功能"——只看核心功能
2. 黄色：标注出你可能会卡住的地方（比如"倒计时逻辑我之前没写过"）
3. 绿色：标注出你有把握的地方（比如"按钮组件我写过很多次了"）

现在你有了一个：范围可控（5 天能做完）、技术可控（只用你会的）、风险可控（你知道哪里会卡住、哪里很自信）的计划。这跟 AI 最初给你列的那 30 个功能清单已经完全不同了——因为你在 AI 的"可能"上加了你的"选择"。
:::

:::example{title="常见错误——看看你踩过几个坑？"}
**错误 1：不砍功能就开始写代码。**
> AI 列了 20 个功能 → 你觉得"都想做" → 7 天后做了 15 个，但没有一个是完全做完的。
功能不是"实现了"就算完成——完成了 = 可以演示 + 边界情况处理好了 + 你愿意给别人看。砍到 5 个，把 5 个都做好。

**错误 2：AI 推荐的技术栈照单全收。**
> "AI 说用 Pinia + TypeScript → 我还没学过但应该不难吧" → 3 天在学习新工具，2 天在写代码，0 天在打磨。
你做一个学习项目的首要目标是完成，不是堆砌技术。每引入一个你没学过的东西，你就在给"完成"增加不确定性。

**错误 3：规划做完就丢一边。**
> 花 30 分钟做了规划 → 第二天开始写代码，完全不看规划，写到哪算哪。
规划的价值在**写代码时帮你克制"加功能"的冲动**。写到一半想加个"黑夜模式"——看一下规划——不在核心功能里 → 忍痛不做了，记到"以后再说"清单里。
:::

:::explain{title="四、实际工作中你会怎么用？"}
- **接到新需求：** 产品经理说"我要一个用户反馈收集系统"。你用 AI 展开所有可能的功能（提交反馈、分类、搜索、导出、邮件通知...）。然后在 5 分钟内和 PM 过一遍：核心体验是什么？（提交和查看反馈）两周内能做什么？（提交、列表、简单搜索）这个对话的产出是一个双方都认同的范围——而不是"你先做，做多少算多少"。
- **技术方案设计：** Leader 让你出一个"搜索功能"的技术方案。你把需求贴给 AI："列出 3 种实现方案（前端过滤、后端全文搜索、ElasticSearch），每种方案的适用场景、开发成本、性能表现。"AI 出对比表 → 你根据项目实际约束（团队能力、时间、数据量）做出推荐 → 方案文档 10 分钟搞定。
- **工作量估算：** 你要估算一个功能需要多久。把功能描述给 AI："把以下功能拆成开发步骤，每步估算开发时间（假设中级前端水平，包含自测时间）。"AI 给你参考估算 → 你自己加 30% buffer（因为 AI 总是低估边界情况和沟通成本）。

:::

:::task{title="规划你的项目"}
::::step{id="1"}
选一个你想做的项目。用"三刀法"的标准，写一个 Prompt 让 AI 帮你做规划。Prompt 里要写明：你的技术栈限制、可用时间、不需要的功能。
::::
::::step{id="2"}
拿到 AI 的规划后，用红笔划掉所有非核心功能。用黄笔标出你可能卡住的地方。用绿笔标出你有把握的地方。保留下来的功能不超过 6 个。
::::
::::step{id="3"}
重新排列 AI 给出的开发步骤——按组件依赖关系排，而不是按"看起来合理"排。每一步标注预计用时，确认总和不超过你的可用时间。
::::
::::step{id="4"}
把这个规划发给一个朋友或同学，让 ta 看一遍是否能理解：你要做什么、怎么做、分几步。如果 ta 看不明白——说明你的规划还不够具体，回去再改。
::::
:::


:::recap
AI 做项目规划一定会功能膨胀——30 个功能、8 个技术栈、永远做不完。你的角色是拿刀的人。第 1 刀砍功能——只保留核心体验（"如果这个应用只能做一件事，是哪件？"）。第 2 刀砍技术栈——只用你会的（每多一个不熟悉的技术，失败概率翻一倍）。第 3 刀砍步骤——按依赖关系重排（被依赖的先做，独立的后面做）。AI 铺开选项，你做出选择。一个好规划的标准不是"覆盖了多少"，而是"能在一周内做完"。

:::
