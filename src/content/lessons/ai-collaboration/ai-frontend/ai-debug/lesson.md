# 用 AI 调试和解释错误

:::analogy
调试不是不犯错——是每次报错都能看懂原因，下次不再犯同样的错。AI 就是那个帮你翻译报错信息、分析根因的"老手"。
:::

:::explain{title="一、AI 是你的调试搭档"}
传统的调试流程：看到报错 → 看报错信息 → 看不懂 → 复制报错到搜索引擎 → 看 StackOverflow → 试三个方案 → 修好。
AI 时代的调试流程：看到报错 → 把报错+相关代码一起贴给 AI → "帮我分析为什么报这个错，怎么修" → AI 解释原因并给出修复方案 → 你验证。
节省的时间不只是在"搜索"环节。更重要的是：**AI 把"答案"和"解释"一起给了你。** StackOverflow 的答案经常是"试试这个"——能修好但不知道原因。AI 能告诉你这个错误是怎么产生的、为什么这个修复有效、以及怎么避免以后再犯。
这就是 AI 调试最革命性的地方：**每一次 debug 都是一节一对一的编程课。** 你的调试能力在每次对话中都在增长。
:::

:::explain{title="二、把错误喂给 AI 的正确姿势"}
不要只贴报错信息。报错信息只有"什么错了"，缺少"在哪里错、在什么上下文中错"。
**最小有效信息：**
1. **报错信息（完整）**——不要截取，TypeError 的前半句和后半句都重要
2. **相关代码（不是全部代码）**——报错涉及的函数或组件
3. **你在做什么**——"用户点击提交按钮后" 或 "页面加载时" 或 "调用 API 后"
4. **预期行为 vs 实际行为**——"我期望它更新列表，但它白屏了"
把这四样东西一起贴给 AI，它的诊断准确率会从"碰运气"变成"大概率正确"。
**示例：**
> 报错：`TypeError: Cannot read properties of undefined (reading 'map')` at `TodoList.vue:23`
> 代码：`const items = props.todos.map(...)`
> 场景：页面首次加载时出现
> 预期：显示 todo 列表
>
> 帮我分析原因并修复。
:::

:::explain{title="三、AI 的诊断也需要验证"}
AI 给的修复方案可能是对的，也可能是错的，还可能看起来对但引入了新问题。
**验证三步：**
1. **AI 解释的原因合理吗？** 读一遍它的分析——逻辑链完整吗？有没有跳跃？
2. **应用修复后，bug 真的消失了吗？** 不只是原来的场景，相关的场景也测一下。
3. **修复有没有副作用？** 改了这里，别的地方有没有受影响？跑一遍主要功能。
**重要心态：** 如果你用了 AI 的修复方案但没理解为什么这样修——那你只是在祈祷，不是在调试。下次遇到类似问题你还是不会修。反之，如果你每次 Debug 都让 AI 解释原因，一个月后你会发现自己能独立诊断 80% 的常见错误。
**AI 是最好的调试老师，只要你不只是复制粘贴，而是追问为什么。**
:::

:::recap
把报错信息、相关代码、在做什么、预期和实际行为这四样东西一起贴给 AI，它的诊断准确率会大幅提升。AI 最好的地方不是帮你修 bug，而是把原因和修复一起讲给你听——每次 debug 都是一节一对一的编程课。
:::
