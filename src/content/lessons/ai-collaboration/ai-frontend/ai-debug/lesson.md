# 用 AI 调试和解释错误

:::analogy
调试不是不犯错——是每次报错都能看懂原因，下次不再犯同样的错。AI 就像那个可以随时问"这里为什么报错"的老手——但前提是你不能只复制粘贴，你得追问为什么。

:::

:::prerequisite
你已经写过一些前端代码，遇到过至少 5 次浏览器控制台的红色报错。你知道 `console.log` 和断点调试的基本用法。

:::

:::explain{title="一、你的问题"}
代码崩了，控制台一行红字。你盯着 `TypeError: Cannot read properties of undefined (reading 'map')`，不知道这行报错到底在说什么。你去搜索引擎搜，找到 5 个 StackOverflow 答案，3 个是"试试这个"，2 个不适用你的场景。你试了其中一个方案——bug 修好了。但你不确定为什么修好了，下次遇到类似问题还是不会修。你需要的是"修好 + 理解原理"，而不只是"修好"。
:::

:::explain{title="二、解决方案：调试对话四件套"}
把一个 bug 贴给 AI 时，不要只贴报错信息。报错信息只知道"what"（什么错了），不知道"where and why"（在哪里、为什么）。你需要贴四样东西：

### 调试四件套

1. **完整的报错信息（不要截取）。** `TypeError` 的前半句和后半句都重要。堆栈跟踪（Stack Trace）里的文件名和行号尤其关键。
2. **相关的代码（不是全部代码）。** 报错涉及的函数或组件。如果代码超过 50 行，标注出"报错出现在第 23 行"。
3. **触发场景。** "用户点击提交按钮后" 还是 "页面首次加载时" 还是 "路由切换时"——这个信息让 AI 从"猜测"变成"定位"。
4. **期望行为 vs 实际行为。** "期望更新列表，实际页面白屏" 或 "期望弹出确认框，实际没有任何反应"——差距描述得越精确，AI 的诊断越准确。

### 完整例子

**坏的贴法：**
> 报错了 TypeError，帮我看看。

**好的贴法（四件套）：**
```
报错：TypeError: Cannot read properties of undefined (reading 'map')
位置：TodoList.vue:23
相关代码：
  const items = props.todos.map(todo => todo.text)
场景：页面首次加载时出现
期望：显示 todo 列表（即使为空也应该显示"暂无数据"）
实际：页面白屏

帮我分析：
1. 为什么会报这个错？
2. `props.todos` 为什么是 undefined？
3. 如何修复？给出修复后的代码。
4. 以后如何避免同类问题？
```

**为什么四件套有效？**

AI 看到完整的报错信息 → 知道错误类型和位置。看到相关代码 → 知道上下文。看到触发场景 → 知道"在什么条件下触发"（页面初始加载时 props 还没传进来）。看到期望 vs 实际 → 知道你的预期（即使为空也应该显示提示）而不仅仅是修复报错。四个信息合一，AI 的诊断不再是"可能的原因有 A、B、C"，而是"大概率是 A，因为..."。
:::

:::explain{title="三、AI 诊断后——你必须做的三步验证"}
AI 给了你分析和修复方案。在把修复代码贴进项目之前，做这三步：

### 第 1 步：AI 的解释逻辑合理吗？

读一遍 AI 的分析。问自己：
- 因果链条完整吗？（"因为 A 所以 B 所以 C"还是一步跳到结论？）
- 有没有逻辑跳跃？（"props 是 undefined" → AI 说"异步数据还没到"——这个推理合理吗？如果 props 是从父组件传入的而不是异步获取的呢？）
- 如果 AI 的解释不对，修复方案也不可能是对的。**先理解原因，再看解决方案。**

### 第 2 步：修复后，bug 真的消失了吗？

应用修复方案后：
- 之前出错的场景下，现在正常吗？
- **相关的场景也测试一下。** 比如修复了"首次加载时 props 为 undefined"的问题，那路由切换后再切回来——正常吗？传空数组——正常吗？
- 如果 bug 消失了但你不知道为什么消失，和没修好一样危险。**修好 + 说不清原因 = 祈祷。**

### 第 3 步：修复有没有副作用？

改了一行代码，至少想一下：
- 这个修改影响哪些其他功能？（比如你改了 props 的默认值——所有依赖这个 props 的组件都受影响）
- 报错虽然没了，但逻辑正确吗？（比如你加了 `props.todos || []`——返回空数组后，后续代码会不会因为空数组而触发另一个 bug？）
- 跑一遍主要功能。不需要完整的回归测试，但至少手动过一遍核心流程。

**一个完整的调试对话**

```
你：
报错：ReferenceError: debounce is not defined
位置：SearchBar.vue:15
相关代码：
  <input @input="debounce(handleSearch, 300)" />
场景：在搜索框输入文字时触发
期望：输入停止 300ms 后执行搜索
实际：控制台报错，搜索不执行

AI：
原因分析：你在模板中直接使用了 `debounce`，但 Vue 模板中只能访问到 setup 中 return 或在 `<script setup>` 中顶层定义的变量。你没有在 setup 中导出 `debounce`，所以模板中访问不到。

修复方案：
1. 在 `<script setup>` 中定义或导入 debounce 函数
2. 或者创建一个包装函数，在 setup 中定义，模板中调用包装函数

修复后代码：
```js
import { debounce } from './utils'

const handleInput = debounce((e) => {
  handleSearch(e.target.value)
}, 300)
```
模板改为：
```html
<input @input="handleInput" />
```

你：
解释一下，为什么 debounce 不能直接在 @input 里调用？

AI：
因为 debounce 返回的是一个新函数。你在 @input="debounce(handleSearch, 300)" 中，每次 input 事件触发时都会重新执行 debounce(handleSearch, 300)，创建一个全新的防抖函数——而不是复用同一个。这样每次都是"第一次调用"，防抖效果完全失效。正确做法是在 setup 中只调用一次 debounce，拿到防抖后的函数，模板中一直用这个函数。

你：
明白了。如果我不用 debounce 工具函数，想手动实现一个防抖，在 Vue 3 里怎么写最地道？

AI：
[给出手动实现 + 解释]
```

这个对话的收获：
1. 修好了 bug。
2. 理解了 debounce 为什么不能直接放在模板里（每次渲染都创建新函数）。
3. 学习了 Vue 3 中的地道写法。
4. 下次遇到类似问题，你能独立解决。
:::

:::example{title="常见错误——看看你踩过几个坑？"}
**错误 1：贴给 AI 的代码太少。**
> 只贴报错信息："Cannot read properties of undefined"，不贴代码。
AI 只能给你笼统的解释（"通常是因为某个值是 undefined"），不能给出具体修复方案。浪费了一次对话。

**错误 2：AI 修好了就不再追问。**
> AI 给了修复 → 修复能跑 → 结束对话。
你在错过最好的学习机会。追问三个问题："为什么报这个错？""你的修复方案背后的原理是什么？""以后怎样避免同类问题？"每个追问都在让你从"会用 AI"变成"会独立解决问题"。

**错误 3：AI 给的方案你改了一个字就用了，但不懂改了什么。**
> AI 说"把第 15 行的 `value` 改成 `currentValue`" → 你改了 → 能跑 → 不问为什么。
一个月后，你在另一个地方写了 `value`，又报同样的错。你再次贴给 AI。循环。
:::

:::explain{title="五、实际工作中你会怎么用？"}
- **生产环境报错：** Sentry/阿里云日志里有一条用户报错，只有堆栈跟踪，没有复现步骤。你把堆栈贴给 AI："根据这个堆栈跟踪，分析可能的出错场景，列出我能尝试的复现步骤。"AI 帮你从堆栈反推用户操作路径。
- **NPM 依赖冲突：** `npm install` 报了一堆 ERESOLVE 错误。把完整报错贴给 AI："分析这些依赖冲突的关系，建议 1-2 个最安全的解决方案，不要建议 --legacy-peer-deps 这种跳过检查的方案。"AI 帮你理清依赖树，你来做最终选择。
- **接手 bug 单：** QA 提了一个 bug——"用户上传图片后预览，偶现图片方向错误"。你把相关代码（上传组件、预览组件、EXIF 处理函数）贴给 AI："根据这段代码分析，为什么上传的图片预览方向可能不正确？重点检查 EXIF 方向数据的处理逻辑。"AI 可能比你更快发现——没有处理 EXIF Orientation 字段。

:::

:::task{title="调试对话实战"}
::::step{id="1"}
找一个你之前遇到过的 bug（最好是你花了不少时间才解决的）。把这个 bug 当作你还没解决的状态，用"调试四件套"格式贴给 AI。
::::
::::step{id="2"}
看 AI 的诊断和修复方案。对比：AI 的方案和你当时实际用的方案一样吗？哪个更简洁？哪个更根本（修的是根因还是表面现象）？
::::
::::step{id="3"}
追问至少 2 个"为什么"：为什么报这个错？为什么这个修复有效？有没有更根本的解决方案？（比如与其在调用处加空值检查，不如在数据源头保证它不为空）
::::
::::step{id="4"}
记录这次调试对话的收获。写三句话：我原来不知道什么？现在我理解了什么？下次遇到类似情况我会怎么做？
::::
:::


:::recap
把 bug 贴给 AI 时用"调试四件套"：完整报错信息、相关代码、触发场景、期望 vs 实际行为。AI 给出修复后，做三步验证：解释合理吗、bug 真的消失了吗、有没有副作用。最重要的原则：修好只是及格，修好 + 理解为什么修好才是学到了。每次 Debug 后追问三个"为什么"——三个月后，你会发现 80% 的常见报错你不需要 AI 就能独立诊断。

:::
