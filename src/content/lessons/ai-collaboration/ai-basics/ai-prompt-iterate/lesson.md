# Prompt 迭代与对话

:::analogy
第一次点菜说"来碗面"，第二次说"少辣、多醋"，第三次说"面硬一点、汤多一点"。你从来不会第一次就点对——和 AI 协作也一样，第一版 Prompt 几乎从来不是最优解。
:::

:::prerequisite
你已经学过 Prompt 的四个原则（具体、给上下文、拆步骤、给示例），知道怎么写一个好的初始 Prompt。
:::

## 一、你的问题

你写了自认为不错的 Prompt，AI 的回复还是不对。你的第一反应可能是"AI 不行"或"我写的 Prompt 不行"。然后你放弃，自己手写去了。但真正的问题不是 Prompt 不够好——是**你把协作当成了一次性投递，而不是多轮对话**。

## 二、解决方案：Iterate, Don't Perfect

AI 协作的核心不是"写出完美 Prompt"，而是这个循环：

```
写 Prompt → 看输出 → 找差距 → 修正 Prompt → 看新输出 → 满意为止
```

:::example{title="一个真实的迭代过程"}
假设你要做一个响应式导航栏。

**第 1 轮：模糊需求**
```
写一个导航栏。
```
AI 输出：一个水平 `<ul>` 列表，5 个 `<li>`，蓝色链接，没有样式，不是响应式的。
你的判断：这只是个链接列表，不是我要的导航栏。我需要：响应式（手机上变汉堡菜单）、当前页面高亮、带 Logo。

**第 2 轮：纠正方向**
```
改进：需要响应式——桌面端水平展开，移动端（<768px）显示汉堡菜单按钮，点击展开垂直菜单。当前页面的链接用不同颜色高亮。左上角有一个 Logo 占位区域。
```
AI 输出：加上了 `@media` 查询和 JavaScript 切换逻辑。但 JS 代码用了 `document.querySelector` 和 `addEventListener`——在 Vue 项目里这是反模式。
你的判断：功能思路对了，但实现方式不对。我需要 Vue 的响应式写法。

**第 3 轮：细化技术方案**
```
改用 Vue 3 Composition API 重写：
- 用 ref(false) 管理菜单开关状态
- 用 :class 绑定高亮样式
- computed 判断当前路由
- 模板中 v-if / v-show 控制移动端菜单显示
```
AI 输出：一个干净的 Vue 3 导航组件，`<script setup>`、`ref`、`computed` 都用对了。响应式、高亮、汉堡菜单都有了。
你的判断：代码质量可以了，但 CSS 的 transition 时长 0.3s 太慢，汉堡菜单的动画僵硬。

**第 4 轮：微调细节**
```
transition 从 0.3s 改成 0.15s，菜单展开动画用 max-height 过渡（从 0 到 500px），不要用 opacity。
```
AI 输出：调整了动画参数。现在点击汉堡菜单，菜单顺滑地滑下来。

**四轮迭代，每轮只解决 1-2 个具体问题。** 如果你第一轮就想写出完美 Prompt，你需要预测所有四个问题——而你根本不知道这些问题在没看到输出之前。所以：**先让 AI 生成点什么，不管质量多差。然后你在看到具体输出的基础上，精确地指出哪里不对。这才是高效的迭代。**
:::

:::explain{title="迭代的底层逻辑"}
迭代之所以有效，是因为你每次只需要做一件事：**把输出和你想要的之间的差距，用一句话描述出来。** 这比"在设计稿还没出来之前就描述清楚你要什么"容易一百倍。就像你更擅长从 10 件衣服里挑出最喜欢的那件，而不是凭空描述你喜欢的衣服长什么样。
:::

## 三、常见错误

**错误 1：看到第一次输出不满意就放弃。**
> Prompt → AI 输出不行 → "AI 不好用" → 关掉。
AI 的第一次输出只是起点，不是终点。你的价值在第二轮、第三轮——你看到了差距，知道怎么纠正。

**错误 2：一次反馈说太多问题。**
> "颜色不对、间距太大、动画太慢、按钮位置错了、字体应该用系统默认、hover 效果不够明显..."
AI 会试图一次性修正所有问题，结果可能哪个都没修好，或者修了 A 坏了 B。正确做法：一轮只修 1-2 个问题。

**错误 3：改了需求不重新描述。**
> "改一下" → AI 不知道你要改什么，可能会把已经对的部分也改坏。
每轮都说清楚：保留什么、改什么、改成什么样。比如："保留现有的 props 接口和组件名，只把内部的 `fetch` 改成 `async/await` 写法。"

:::example{title="迭代的四个追问句式"}
当 AI 的输出不对时，不要只说"不对"，用这四个句式精确描述：

1. **纠偏式：** "不对，我要的不是 XXX，而是 YYY。保留现有的[对的部分]，只改[错的部分]。"
2. **质疑式：** "你为什么在这里用 `useEffect`？在 Vue 3 里 `watch` 或 `computed` 是不是更合适？"
3. **深挖式：** "你写的这个排序算法，当数组长度超过 10000 时性能如何？帮我分析一下时间复杂度。"
4. **化简式：** "这个实现太复杂了。有没有更简单的方法？我不想引入第三方库。"
:::

## 四、实际工作中的场景

- **UI 还原：** 设计师给了你一个页面设计稿。你用 AI 生成第一版 HTML/CSS，然后在对话里逐轮调整——"header 的背景色改成 #F8F9FA""卡片间距改成 16px""按钮的圆角从 4px 改成 8px"。你就像一个导演，AI 是执行灯光和道具的工作人员。你做的是"感觉不对——调一下——好了"而不是"我先描述清楚所有细节再动手"。
- **Code Review 后的修改：** 同事 Review 了你的 PR，提了 5 条意见。你把同事的评论直接贴给 AI："按照这 5 条 Review 意见修改上面的代码。"AI 改完后你逐条核验——改对了没、有没有引入新问题。
- **性能调优：** 你怀疑某段代码有性能问题，但不确定。你把代码贴给 AI："分析这段代码的性能瓶颈。"AI 给出分析。你选择 1-2 个点："先优化这个循环，用 Map 替代数组的 find。改完给我看前后对比。"

:::task{title="练习迭代协作"}
::::step{id="1"}
选一个 50-100 行的功能——可以是表单验证、Todo 列表、或数据表格。用你目前最好的 Prompt 让 AI 生成初版代码。
::::
::::step{id="2"}
审查输出，找出至少 3 处可以改进的地方（功能、性能、可读性、边界处理）。按优先级排序：哪个最严重先修哪个。
::::
::::step{id="3"}
进行至少 3 轮迭代。每轮只修 1 个问题。每轮记录：你提了什么修改要求、AI 改成了什么样、你是否满意。
::::
::::step{id="4"}
对比第 1 轮和第 3 轮的代码质量。写一句话："迭代前最大的问题是什么？迭代后最大的改善是什么？"
::::
:::

:::recap
第一版 Prompt 几乎从来不是最优解——这是正常的，不是你的失败。AI 协作的核心是迭代：写 Prompt、看输出、找差距、修正 Prompt，循环直到满意。每轮只修 1-2 个问题，用精确的语言描述"保留什么、改什么、改成什么样"。你的价值不在第一次 Prompt（AI 不知道你想做什么），在第二次、第三次（你看到了差距，知道怎么纠正）。
:::
