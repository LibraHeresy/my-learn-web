# 写好 Prompt 的核心原则

:::music-analogy
「好的指挥不需要说出每一个音符——只需要指出方向、速度、情绪，乐团就知道怎么演奏。好的 Prompt 也一样。」
:::

:::explain{title="一、原则一：具体，再具体"}
坏 Prompt 像一个模糊的需求单："帮我写个按钮。"
AI 被迫猜。它猜你要什么颜色、什么大小、什么文案、什么功能。猜错的概率极高。
好 Prompt：
> 写一个 Vue 3 `<template>` 中的 icon 按钮组件。圆角 8px，背景浅蓝 #E8F0FE，文字深蓝 #1A73E8，hover 时背景变为 #D2E3FC。按钮内容是一个带 emoji 和短文本的组合，通过 prop 传入。尺寸 small（padding 6px 12px）和 medium（padding 10px 20px）两档，通过 prop 控制。
四种信息的密度完全不同：
- 坏 Prompt：6 个词的模糊需求
- 好 Prompt：明确了技术栈、样式参数、交互行为、组件接口、尺寸变体
**原则：把 AI 当成一个很能干但完全不了解你项目的新同事。** 你不说清楚，它一定猜错。你给的上下文越具体，它的输出越接近你要的东西。
:::

:::explain{title="二、原则二：给上下文"}
AI 不知道你的项目是用 React 还是 Vue，不知道你的 CSS 是用 Tailwind 还是原生 CSS，不知道你的团队有没有命名规范。你必须告诉它。
对比：
**没有上下文的 Prompt：** "写一个数据获取的 hook。"
**有上下文的 Prompt：** "我在用 Vue 3 Composition API + TypeScript。当前项目的命名规范是 camelCase，函数以 `use` 开头。写一个 `useFetch` 组合式函数，接受 URL 参数，返回 `{ data, loading, error }` 三个 ref，包含请求取消逻辑。"
加了三行上下文，AI 的产出就从"可能能用"变成了"直接能用"。这些额外信息对你来说是免费输入的（你本来就知道你在用什么技术栈），对 AI 来说是决定性的（它不用猜了）。
**原则：Prompt 的第一句话不是描述需求，是描述环境。**
:::

:::explain{title="三、原则三：分步骤"}
给 AI 一个复杂任务，就像让一个陌生人做一个复杂项目——如果你一次性说完所有要求，他会崩溃。
坏 Prompt："帮我做一个完整的 Todo 应用，包含添加、删除、标记完成、过滤、搜索、持久化到 localStorage、响应式设计。"
这种 Prompt 的结果通常是：大部分功能勉强能用，但每个都有小 bug，整体结构混乱，不好维护。
正确方式：拆成多个对话。
> **第 1 步：** "写一个 Todo 应用的 HTML 结构和 Vue 3 响应式数据，先只实现列表展示。"
> **第 2 步：** "加上添加功能：一个输入框和一个添加按钮。"
> **第 3 步：** "给每个 todo 项加上删除和标记完成功能。"
每一步都验证、确认没问题，再进入下一步。你自己写代码的时候也是这样的——你不会一次写完一千行然后 run。
**原则：把大任务拆成 AI 能一口吃完的小任务。每步验证，逐步构建。**
:::

:::explain{title="四、原则四：给示例（Few-shot）"}
你想让 AI 生成一种特定风格的代码，但用语言描述"风格"很难。最简单的方式：**给它看一个例子。**
> 我需要为下面这些 API 路径生成类型定义。格式参考：
>
> 示例：
> `/api/users/:id` → `GET /api/users/{userId}`
> 
> 待处理列表：
> - `/api/orders/:orderId`
> - `/api/orders/:orderId/items/:itemId`
> - `/api/products/:productId/reviews`
AI 看了这个例子，立刻理解了格式规则，然后准确地生成了剩下的。一个例子胜过一千字的描述。
**原则：如果你想要的输出有特定的格式或风格，给 1-2 个示例。比用语言描述高效十倍。**
这四个原则——具体、给上下文、分步骤、给示例——可以用在所有 AI 工具上，无论你用 ChatGPT、Claude、Copilot 还是国产工具。它们不是"技巧"，是**和 AI 有效协作的方法论**。
:::
