# 先规划再动手 — 用注释画出你的设计草图

:::analogy
写代码和写作文一样--先列提纲（注释），再填内容（代码）。直接上手就写，写到一半发现方向错了，比先花 5 分钟规划浪费的时间多十倍。
:::

:::prerequisite
**本节你需要知道这些词：**

- HTML 注释：`<!-- 我是注释 -->`
- CSS 注释：`/* 我是注释 */`
- JS 单行注释：`// 我是注释`
- `querySelectorAll` -- 获取所有匹配选择器的元素，返回 NodeList
:::

:::explain{title="先看问题：不规划就直接写会怎样？"}

假设产品经理给你一个需求："做一个音乐收藏页面，顶部有标题，中间是 3 张卡片，底部显示统计数量。"

不规划、直接写代码的典型过程：

```html
<!-- 随手就写，想到哪写到哪 -->
<h1>我的音乐</h1>
<div class="card">曲目A</div>
<div class="card">曲目B</div>
<p>共 2 首</p>
<div class="card">曲目C</div>  <!-- 咦，这个怎么放这里？应该和上面卡片在一起 -->
<!-- 然后开始到处挪标签，CSS 也乱了，JS 的 querySelector 也找不到了... -->
```

结果：30 分钟后，你发现结构不合理，卡片应该包在一个容器里方便 CSS 布局。于是大改 HTML，CSS 重写，JS 重写。**实际有效的代码量可能只有 20%，其余 80% 都是返工。**

这个问题的根源不是技术不够，而是**没有规划**。

:::

:::explain{title="解决方案：用注释先画草稿"}

拿到需求后，第一步不是写代码，而是**写注释规划结构**。

**HTML 规划注释：**

```html
<!-- 页面分为三个区域：
  1. 顶部标题区 -- 标题 + 副标题
  2. 中间卡片列表 -- 用容器包裹 3 张卡片
  3. 底部统计区 -- 显示"共 X 条收藏"
-->

<!-- ===== 顶部标题区 ===== -->
<header>
  <h1>我的音乐收藏</h1>           <!-- 主标题 -->
  <p>记录那些打动我的旋律</p>     <!-- 副标题 -->
</header>

<!-- ===== 中间卡片列表区 ===== -->
<main class="card-list">           <!-- 卡片容器，CSS 用它做 flex 布局 -->
  <!-- 卡片1：封面、曲名、作者 -->
  <!-- 卡片2：封面、曲名、作者 -->
  <!-- 卡片3：封面、曲名、作者 -->
</main>

<!-- ===== 底部统计区 ===== -->
<footer>
  <p>共 <span id="count">3</span> 条收藏</p>  <!-- 数量用 span 包起来，JS 方便改 -->
</footer>
```

你看，注释就像施工图纸--标注了每个区域做什么，CSS 和 JS 看到这些注释就知道该往哪里写。

**CSS 规划注释：**

```css
/* ===== 顶部标题区 ===== */
header {
  text-align: center;       /* 标题居中 */
}
header h1 {
  color: #8B0000;           /* 暗红主色 */
}

/* ===== 卡片列表区 ===== */
.card-list {
  display: flex;            /* 卡片横向排列 */
  gap: 20px;                /* 卡片间距 */
}
.card {
  background: #FFFAF2;      /* 米白卡片背景 */
  border-radius: 8px;       /* 圆角 */
  padding: 16px;            /* 内边距 */
}

/* ===== 底部统计区 ===== */
footer {
  text-align: center;       /* 居中 */
  color: #666;              /* 灰色文字，弱化视觉权重 */
}
```

**JS 规划注释：**

```js
// 1. 获取页面元素
// 2. 准备数据（口号数组）
// 3. 给标题绑定点击事件 -- 点击后随机切换口号
// 4. 统计卡片数量并显示
```

注释写完后，你会发现接下来只是"填空"--把每一行注释下面的代码补上。思路不会断，因为你已经规划好了。

:::

:::explain{title="常见错误"}

**错误 1：注释描述"做了什么"而非"为什么"**

```js
// ❌ 错误：描述操作，废话注释
// 把 3 赋给 x
let x = 3;
```

```js
// ✅ 正确：描述意图
// 默认显示 3 张卡片（移动端一屏刚好容纳）
let cardCount = 3;
```

**错误 2：注释和代码不同步**

```js
// ❌ 错误：注释说"随机选曲"，实际代码是固定第一首
// 随机选取一首曲目
let piece = pieces[0];  // 永远是第一首！
```

```js
// ✅ 正确：改代码时同步改注释
// 默认展示第一首曲目（首页默认推荐）
let piece = pieces[0];
```

**错误 3：把规划注释当作"写完之后补"**

注释的价值在写代码**之前**。写完代码再补注释等于画完房子再画图纸--毫无意义。

:::

:::explain{title="实际工作中你会用这个来..."}

- **接到 feature request（功能需求）时**：把需求文档里的验收标准（acceptance criteria）直接写成 JS 注释。比如需求是"用户点击标题，标题随机变成一句口号"，你就写 `// 点击标题 -> 随机切换口号`。写完注释让同事看一眼，确认理解正确再动手。
- **Code Review（代码审查）时**：同事看你的代码，先看注释规划就知道你的思路，不用从代码反推你的意图。
- **三个月后回来改自己的代码时**：注释让你 30 秒内回忆起当时的思路，而不是盯着代码发呆十分钟。

:::
